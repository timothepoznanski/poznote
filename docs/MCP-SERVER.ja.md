# Poznote MCPサーバー

PoznoteのMCP（Model Context Protocol）サーバーです。自然言語を使って、AIでノートを管理できます。

このサーバーが対応しているのは**HTTPトランスポートのみ**です（MCP Streamable HTTP）。

> [!TIP]
> Poznoteの中で、ローカルモデル（Ollamaなど）と直接チャットしたい場合は、MCPサーバーは必要ありません。代わりに、組み込みの[AIアシスタント](AI-ASSISTANT.ja.md)を使ってください（「設定 > 管理ツール > AIアシスタント」）。MCPサーバーは、MCPに対応した*外部の*アシスタントをノートに接続するためのものです。Ollama単体はモデルの実行環境であってMCPクライアントではないため、MCPサーバーに直接は接続できません。

## 仕組み

MCPサーバーは、AIアシスタントとPoznoteインスタンスのあいだの橋渡しをします。

### 構成要素

- **`server.py`**：MCPサーバー（HTTP / Streamable HTTP）
  - MCPエンドポイントを`http://127.0.0.1:8045/mcp`で公開
  - ノート管理用のツール（アクション）を定義
  - AIとPoznote APIのあいだの呼び出しを仲介

- **`client.py`**：Poznote REST API用のHTTPクライアント
  - HTTPリクエスト（GET、POST、PATCH、DELETE）を実行
  - 共有のMCPサービストークンを使って、Poznote APIの認証を処理

### 通信の流れ

1. AIアシスタント（VS Code CopilotまたはClaude CLI）がMCPサーバーに接続
2. MCPサーバーがPoznote REST APIを呼び出す
3. 結果がAIアシスタントに返される

ブラウザーで開いているPoznoteのタブには、MCPによる変更が数秒以内に反映されます。サイドバーのツリーと開いているノートがその場で更新されます（ノートに未保存の編集がある場合は、再読み込みを促すバナーが表示されます）。ブラウザーで開いているだけのノートは、MCPによる書き込みを妨げません。同じアカウントの別のユーザー、または公開リンクの訪問者が編集中のノートだけが、HTTP 423エラーを返します。

## 機能

### ツール（アクション）
- `get_note`：IDを指定して、特定のノートを内容ごと取得
- `list_notes`：ワークスペースのノートを1ページずつ一覧表示（`limit`/`offset`を指定。結果にはワークスペースの実際の`total`が含まれる）
- `search_notes`：テキストでノートを検索。作成日の範囲も指定可能
- `create_note`：新しいノートを作成。テンプレートからの作成や、期限・リマインダーの設定も可能
- `update_note`：既存のノートを更新。移動や、期限・リマインダーの設定も可能
- `delete_note`：IDを指定してノートを削除
- `get_reminder`：ノートに現在設定されているリマインダーを取得
- `set_reminder`：ノートのリマインダーを設定、または置き換え。繰り返しの間隔も指定可能
- `remove_reminder`：ノートのリマインダーを解除
- `list_reminders`：すでに通知され、まだ残っているリマインダーの通知を一覧表示（画面のベルアイコンの通知一覧と同じもの）。これから通知されるリマインダーは一覧表示できない
- `list_tasks`：タスクリストのノートのタスクを、ID、期限、フラグとともに一覧表示
- `list_all_tasks`：ワークスペースのすべてのノートから未完了のタスクを、急ぐものから順に一覧表示。絞り込みの条件（期限、重要、完了済み、ノート内のチェックリスト）も指定可能
- `add_task`：タスクリストのノートにタスクを1件追加。期限とリマインダーも指定可能
- `update_task`：タスクを1件更新（テキスト、期限、リマインダー、重要フラグ）
- `complete_task`：タスクを完了にする、または未完了に戻す
- `delete_task`：タスクリストのノートからタスクを1件削除
- `add_subtask`：タスクリストのノートのタスクにサブタスクを追加
- `update_subtask`：サブタスクの名前を変更、または完了・未完了を設定
- `delete_subtask`：タスクのサブタスクを1件削除
- `create_folder`：名前またはパスを指定してフォルダーを作成（`folder_path="Projects/2026/Q3"`なら、途中の階層もまとめて1回で作成）。`is_diary=true`で日記のルートフォルダーも作成可能
- `list_folders`：ワークスペースのすべてのフォルダーを、パスと日記フラグとともに一覧表示
- `list_workspaces`：利用できるすべてのワークスペースを一覧表示
- `list_tags`：ノートで使われているタグを、重複なしですべて一覧表示
- `list_templates`：`create_note`の`from_template_id`で元にできるテンプレートのノートを一覧表示
- `get_trash`：ゴミ箱にあるすべてのノートを一覧表示
- `empty_trash`：ゴミ箱のすべてのノートを完全に削除
- `delete_trash_note`：ゴミ箱全体を空にするのではなく、ゴミ箱のノートを1件だけ完全に削除
- `restore_note`：ゴミ箱からノートを復元
- `list_snapshots`：ノートについて保存されている過去のリビジョンを一覧表示。AIやMCPが書き換える前に毎回取られる安全用スナップショットも含む
- `get_snapshot`：ノートを変更せずに、過去のバージョンの1つの内容を読み取る
- `restore_snapshot`：ノートをスナップショットの1つの状態に戻す（`snapshot_key`または`date`が必須）
- `duplicate_note`：既存のノートを複製
- `toggle_favorite`：ノートのお気に入りの状態を切り替え
- `list_attachments`：特定のノートの添付ファイルをすべて一覧表示
- `add_attachment`：base64の内容から、ファイルをノートに添付（画像、ログ、PDFなど）
- `move_note`：ノートを別のワークスペースやフォルダーに移動。IDは変わらない
- `move_folder`：フォルダーを（サブフォルダーとノートごと）別の親フォルダーの下や、別のワークスペースに移動
- `move_note_to_folder`：ノートを特定のフォルダーに移動
- `remove_note_from_folder`：ノートを現在のフォルダーから外す（ルートに移動）
- `share_note`：ノートを公開リンクで共有し、公開URLを取得
- `unshare_note`：ノートの公開リンクでの共有を解除
- `get_note_share_status`：ノートの現在の共有状態と公開URLを取得
- `get_folder_share_status`：フォルダーの現在の共有状態と公開URLを取得
- `list_shared`：公開リンクで共有しているすべてのノートとフォルダーを一覧表示
- `list_shared_with_me`：他のユーザーがこのプロフィールと共有しているノートとフォルダーを一覧表示
- `get_backlinks`：特定のノートにリンクしている（参照している）ノートをすべて取得
- `convert_note`：ノートの形式をHTMLとMarkdownのあいだで変換
- `rename_folder`：既存のフォルダーの名前を変更
- `delete_folder`：フォルダーを削除し、中のノートをゴミ箱に移動
- `create_workspace`：新しいワークスペースを作成
- `rename_workspace`：既存のワークスペースの名前を変更
- `delete_workspace`：ワークスペースを削除（最後の1つは削除できない）
- `get_git_sync_status`：Git同期（GitHub/GitLab/Forgejo）の現在の状態を取得
- `git_push`：ローカルのノートを、設定したGitリポジトリに強制的にプッシュ
- `git_pull`：設定したGitリポジトリから、ノートを強制的にプル
- `get_system_info`：Poznoteのインストールのバージョン情報を取得
- `list_backups`：利用できるすべてのシステムバックアップを一覧表示
- `create_backup`：新しいシステムバックアップの作成を開始
- `restore_backup`：バックアップファイルを復元（現在のユーザーデータは置き換えられる）
- `delete_backup`：特定のバックアップファイルを削除
- `get_app_setting`：アプリケーションの特定の設定の値を取得
- `update_app_setting`：アプリケーションの特定の設定の値を更新

**呼び出し先のワークスペース**。`create_note`、`create_folder`、`list_folders`では、必ず`workspace`を指定してください（フォルダーは必ずどれか1つのワークスペースに属します）。確実に狙ったワークスペースにするには、これしか方法がありません。省略した場合、サーバーは決まった順序でワークスペースを決め、推測はしません。まず、`mcp_default_workspace`の設定値が存在するワークスペースの名前であれば、そのワークスペースを使います。次に、アカウントのワークスペースが1つだけなら、それを使います。ワークスペースが複数あって設定もない場合は、並べたときにたまたま先頭に来るワークスペースにノートを置くのではなく、呼び出しを拒否し、ワークスペースの一覧を返します（以前は、この先頭のワークスペースが勝手に変わることがありました。たとえば、ノートを初めてアーカイブしたときに「Archives」が作られると、先頭が変わりました）。既定のワークスペースは`update_app_setting("mcp_default_workspace", "<name>")`で設定します。

**添付ファイル**。`add_attachment(note_id, filename, content_base64)`は、Web UIでドラッグアンドドロップしたときとまったく同じように、ファイルをノートに保存します。そのため、生成したグラフやログファイルを、人の手を介さずに添付できます。内容として`data:` URIも受け付けます。Poznote自体のルールは引き続き適用されるので、実行可能な形式のファイルや、ストレージの容量の上限に達している場合は、理由を添えて拒否されます。ファイルのバイト列はbase64でエンコードされてツールの呼び出しの中で送られるため、このツールのアップロードの上限は25MBです。それより大きいファイルには、Web UIを使うよう案内します。

**移動**。`move_note`と`move_folder`は移動するもので、コピーはしません。ID、内容、履歴、ノートを指しているリンクは、すべてそのまま残ります。`update_note`では、`workspace`は*ノートを探す*ワークスペースを指定するもので、ノートを移動させる引数は`target_workspace`です。移動先のフォルダーを指定せずに別のワークスペースに移ったノートは、移動先のワークスペースのルートに置かれます。元のフォルダーは、移動元のワークスペースに属しているためです。フォルダーは、サブフォルダーとその中のすべてのノートを連れて移動します。

**フォルダー**。フォルダーを受け取るツールは、どれも同じ形式で受け取ります。名前か、スラッシュ区切りのパスです。`create_note(folder="Diary/2026/08")`は、途中で足りない階層を作成します。`create_folder(folder_path=…)`も、フォルダーについて同じことをします。`list_notes(folder_id=…)`はサーバー側で一覧の範囲を1つのフォルダーに絞るので、`total`はそのフォルダーだけの件数になります。名前だけを指定した場合、ワークスペースの中にその名前のフォルダーが1つしかなければ、どの階層にあってもそのフォルダーを指し、ルートに2つ目のフォルダーを作ることはありません。同じ名前のフォルダーが複数ある場合は、呼び出しを拒否して、それらを一覧で返します。その場合は、フルパスかIDを指定してください。

**日記**。日記は、単にDiaryという名前のフォルダーではありません。`is_diary`フラグの付いたルートフォルダーです。画面で日記のエントリを作成すると、日付の付いたノートは、このフラグの付いたルートフォルダーに振り分けられます。日記は`create_folder(folder_name="Journal", is_diary=true)`で作成でき、どのフォルダーが日記かは`list_folders`でわかります。既存のルートフォルダーと同じ名前を指定すると、そのフォルダーが日記になり、中のノートはそのまま残ります。日記のエントリ自体は普通のノートなので、`create_note(folder="Journal/2026/09")`で振り分けます。

**テンプレート**。テンプレートは、`Templates`という名前のフォルダー（その下の階層ならどこでもかまいません）か、その名前のワークスペースのどこかに置いた普通のノートです。この名前は、同梱されているすべての言語で認識されるので、`Modèles`や`テンプレート`という名前のフォルダーでも動作します。`list_templates`はテンプレートをIDとともに返し、`create_note(from_template_id=…)`はテンプレートから新しいノートを、テンプレートと同じ形式で作成します。`note_type="markdown"`を指定すると、HTMLのテンプレートは、エディターで`/template`コマンドを使ったときと同じように変換されます。テンプレートから、タスクリストや図（Excalidraw）のノートを作ることはできません。`content`も指定すると、その内容はテンプレートの本文の後ろに追加されます。

**リマインダーとタスク**。`reminder_at`（`create_note`/`update_note`と`set_reminder`で指定）は、`2026-09-01T09:00:00+02:00`のようなISO形式の日時です。オフセットを含めてください。含めないと、時刻はUTCとして扱われます。タスクの期限（`due_at`）は扱いが異なります。オフセットを付けない現地の時刻で、`YYYY-MM-DD`または`YYYY-MM-DDTHH:MM`の形式で指定し、ユーザーが設定したタイムゾーンで解釈されます。時刻のない日付の場合は、09:00に通知されます。繰り返しの間隔は`<count><unit>`の形式で指定し、単位は`i`/`h`/`d`/`w`/`m`/`y`です。たとえば`30i`、`1d`、`2w`のように指定します。

タスク用のツールは、1回に1件のタスクを扱います。`list_tasks`を呼び出してタスクのIDを取得してから、`add_task`、`update_task`、`complete_task`、`delete_task`を呼び出してください。それぞれの呼び出しはそのタスクだけを送るので、クライアントがタスクリストを読み取って、配列全体を新しく送り返すことはありません。また、別々のタスクを編集している2つの呼び出し元が、互いの変更を上書きすることもありません。Poznoteはノートのタスクを1つのJSON配列として保存していて、サーバーは呼び出しのたびにそれを書き直すため、1回の呼び出しの処理量は、やはりリストの長さに応じて増えます。通知は自動で同期され、タスクを完了または削除すると、そのタスクの待機中のリマインダーも解除されます。タスクにはサブタスクを1階層まで付けられます。`list_tasks`は、サブタスクをそれぞれのIDとともにタスクの`subtasks`配列で返し、`add_subtask`、`update_subtask`、`delete_subtask`で1件ずつ変更できます。サブタスクが持つのはテキストと完了フラグだけで、サブタスクにチェックを入れても、親のタスクが完了になることはありません。

**バージョン履歴と元に戻す操作**。Poznoteは、AIアシスタントやMCPサーバーがノートを書き換える直前に、そのノートの安全用スナップショットを取ります。そのため、`update_note`の結果がよくなかった場合も元に戻せます。`list_snapshots`は、ノートについて保持されているスナップショットを表示します。それぞれに`origin`が付いていて、安全用のコピー（`ai`または`mcp`）を見分けられます。`get_snapshot`はノートに触れずにスナップショットを1つ読み取り、`restore_snapshot`はその内容をノートに戻します。`restore_snapshot`は現在の内容を上書きするので、今日のスナップショットを代わりに使うことはせず、`snapshot_key`または`date`の指定を必須にしています。また、上書きする前の内容を保存しないため、置き換えられる内容は、すでにどれかのスナップショットに残っていない限り失われます。Poznoteの画面では、スナップショットは「リビジョン」と呼ばれます。ユーザーはノートの「リビジョン」ページでリビジョンを閲覧・比較するので、リビジョンやバージョン履歴についての依頼は、これらのツールで扱います。

**複数のノートをまたいだ確認**。`list_tasks`が1つのノートを対象にするのに対し、`list_all_tasks`はワークスペース全体について「残っている作業は何か」に答えます。返す項目は2種類で、`source`で区別します。1つはタスクリストのノートのタスクで、IDは`update_task`や`delete_task`で使えます。もう1つは普通のノートの中に書かれたチェックボックスの項目で、IDはノート内の位置を表すだけなので、これらのツールでは指定できません。`list_reminders`は、すでに通知されていて、まだ閉じられていない通知を返します。APIの上限は50件です。これから通知されるリマインダーを確認するためのものではありません。Poznoteには将来のリマインダー用のエンドポイントがないため、それらは`get_reminder`でノートごとに読み取ります。

ほとんどのツールは、特定のユーザープロフィールを対象にするための、省略可能な`user_id`引数を受け付けます。指定すると、MCPサーバーはそのリクエストに`X-User-ID`ヘッダーを付けて送るので、MCPの全体の環境設定を変えずに、別のプロフィールのノートを作成したり読み取ったりできます。例外はシステム全体を扱うツールの`get_system_info`、`list_backups`、`create_backup`、`delete_backup`で、これらは`user_id`を受け付けません。`user_id`を渡さないときに使われる既定のプロフィールを変えるには、[既定のユーザープロフィール](#既定のユーザープロフィール)を参照してください。

## サーバーのインストール

MCPサーバーは公式のPoznoteの`docker-compose.yml`に含まれていて、自動で起動します。

### 設定

MCPサーバーは、`docker-compose.yml`の既定値を使います：

```bash
# MCPサーバーのポートの既定値は8045
# デバッグログの既定値はfalse
```

Poznoteは、MCPサービストークンを`data/.mcp_token`に自動で生成します。`mcp-server`コンテナーは、共有ボリューム`./data:/var/www/html/data:ro`を通してこのファイルを読み取るので、`.env`にパスワードを置いておく必要はありません。

1回の起動だけポートとデバッグの設定を変えるには、コマンドの前に環境変数を書いて、MCPコンテナーを作り直します：

```bash
POZNOTE_MCP_PORT=9000 POZNOTE_DEBUG=true docker compose up -d --force-recreate mcp-server
```

単に`docker compose restart mcp-server`を実行しても、変更した環境変数は読み込まれません。

#### 用途に合ったモード

MCPサーバーは、3つの方法のいずれかでクライアントを識別します。違いを見分けるポイントは、**リクエストがどのPoznoteアカウントで動作するかを誰が決めるか**です：

| 状況 | モード | アカウントを決めるもの |
|---|---|---|
| 自分ひとりで、同じマシン上のクライアント（VS Code、Claude CLI）を使う | クラシックモード（既定）。[受信用の認証トークン](#受信用の認証トークン)も併用可能 | サーバーの設定：`POZNOTE_USER_ID`（既定はプロフィール`1`）、またはリクエストが`user_id`で指定したプロフィール |
| 複数の人で使う、チャットアプリ（ChatGPT、Claude、Gemini）を使う、またはVS Code / Claude Codeから公開サーバーに接続する | [チャットアプリからのログイン](#チャットアプリからのログインchatgptclaudegemini)（`POZNOTE_MCP_AUTH_PROVIDER=poznote`） | ログインした人：常にその人自身のアカウント |
| IDプロバイダー（Keycloak、Authentikなど）のトークンをすでに持っているエージェント | [呼び出し元ごとの認証](#呼び出し元ごとの認証任意)（`userinfo`または`introspection`） | トークンのIDに結び付いたプロフィール |

複数の人で1つのMCPサーバーを共有するなら、すぐに2つ目のモードを使ってください。クラシックモードでは、どのクライアントもすべてのアカウントにアクセスできます。

#### 既定のユーザープロフィール

既定では、MCPサーバーはユーザープロフィール`1`（最初の管理者）として動作します。サーバーを別のプロフィールに固定するには、コンテナーの起動時に`POZNOTE_USER_ID`を設定します：

```bash
POZNOTE_USER_ID=2 docker compose up -d --force-recreate mcp-server
```

以降のツールの呼び出しは、すべてそのプロフィールに対して行われます。ただし、リクエストで`user_id`引数を明示した場合は、そのリクエストではそちらが優先されます。値は数値のプロフィールIDでなければなりません。それ以外の値は、MCPのログに警告を出したうえで無視され、既定の`1`が使われます。

#### 受信用の認証トークン

既定では、MCPエンドポイントは、到達できるクライアントであれば何でも受け付けます。ポートは`127.0.0.1`にしか公開されていないので、これで安全です。ポートを自分のマシンの外に公開する場合（リバースプロキシ、LAN、ベアメタルへのインストール）は、`POZNOTE_MCP_AUTH_TOKEN`を設定してください。サーバーはすべてのリクエストに`Authorization: Bearer <token>`ヘッダーを求め、ない場合は`401 Unauthorized`を返します：

```bash
# 強力なトークンを一度だけ生成する
openssl rand -hex 32

# .envに書き込む
POZNOTE_MCP_AUTH_TOKEN=paste-the-token-here

# 新しい環境変数を読み込ませるため、MCPコンテナーを作り直す
docker compose up -d --force-recreate mcp-server
```

そのうえで、クライアントの設定にも同じヘッダーを追加します。[VS Code Copilot](VSCODE-COPILOT.ja.md#認証トークンを使う)と[Claude CLI](CLAUDE-CLI.ja.md#認証トークンを使う)を参照してください。前後の空白は無視されるので、シークレットのファイルから読み込んだトークンの末尾に改行があっても動作します。値が空の場合、エンドポイントは誰でも接続できる状態のままになります。どちらのモードが有効かは、起動時のログの行でわかります。

このトークンは`data/.mcp_token`とは別物です。`data/.mcp_token`は、MCPサーバーがPoznote APIに*アクセスする*ために使うもので、こちらは*AIアシスタント*がMCPサーバーに提示しなければならないものです。

#### チャットアプリからのログイン（ChatGPT、Claude、Gemini）

ChatGPT（とCodexアプリ）、Claude Desktopとclaude.ai、Geminiのように、リモートのMCPサーバーに接続するチャットアプリは、貼り付けたトークンを受け付けません。サーバーがOAuthのログインに案内してくれることを前提にしています。`POZNOTE_MCP_AUTH_PROVIDER=poznote`を設定すると、Poznote自身がその役割を担います：

1. アプリで、`https://mcp.example.com/mcp`をコネクターとして追加します。クライアントIDとシークレットの欄は空のままにしておくと、アプリが自分自身を登録します。この設定は多くの場合、アプリの設定画面にカスタムコネクターやリモートMCPサーバーとして用意されています。特定のプランや開発者モードでしか使えないアプリもあります。
2. アプリがPoznoteのログインページを開きます。いつもの方法（パスワード、2要素認証、SSO）でログインします。
3. 同意のページに、アプリの名前、ログイン後に戻る先、使われるアカウントが表示されます。使われるのは常に自分自身のアカウントです（アクセスを許可されているほかのアカウントが使われることはありません）。このページでアクセス権を「閲覧のみ」「閲覧と編集」「フルアクセス」から選びます。この3つは、[ツールのスコープ](#ツールのスコープ)の3つのレベルに対応します。
4. 「許可」をクリックすると、アプリはそのアカウントにだけ、選んだレベルでアクセスするようになります。

このように、1つのMCPサーバーでインスタンス全体をまかなえ、各ユーザーは自分のノート（と共有されたワークスペース）にだけアクセスします。「設定 > マイアカウント > 接続中のアプリ」には接続の一覧が表示され、どの接続も解除できます。全員が貼り付けるためのコネクターのアドレスも、ここに表示されます。

要件：

- チャットアプリはインターネットから接続する（ChatGPTとclaude.aiは各社のサーバーから接続する）ため、MCPサーバーとPoznoteの両方に、そこから**HTTPS**でアクセスできる必要があります。MCPサーバーはリバースプロキシの後ろに、**専用の（サブ）ドメイン**で置いてください（例：`https://mcp.example.com`）。OAuthのディスカバリ用のドキュメントは、そのアドレスのルートで提供されます。プロキシの転送先は、プロキシがどこで動いているかによって異なります：
  - サーバーに直接インストールしている場合：`127.0.0.1:8045`（`docker-compose.yml`が公開するポート、`POZNOTE_MCP_PORT`）に転送します。
  - プロキシ自体がDockerで動いている場合（Nginx Proxy Manager、Traefik、Caddyなど）：`127.0.0.1`はプロキシ自身のコンテナーを指してしまいます。`docker network connect poznote_default <proxy-container>`でプロキシをPoznoteのDockerネットワークに接続し（ネットワークの名前は`docker-compose.yml`があるフォルダーの名前から決まります。`docker network ls`で確認してください）、`mcp-server:8045`に転送します。
- Poznote自身の`/oauth/`のページには、前段に別のログイン（プロキシでのAutheliaやAuthentikによるフォワード認証など）を挟まずにアクセスできなければなりません。アプリはその一部を自分のサーバーから呼び出すので、ログインページを表示するブラウザーがありません。
- `.env`に2つの変数を設定し、コンテナーを作り直します（`docker compose up -d --force-recreate mcp-server`）。古い`docker-compose.yml`はこれらの変数をコンテナーに渡さないので、先に最新のものをダウンロードしてください。正しく設定されていれば、起動時にMCPのログに`OAuth sign-in through Poznote enabled`と表示されます。

```bash
POZNOTE_MCP_AUTH_PROVIDER=poznote
# MCPサーバーの公開URL（/mcpは付けない）
POZNOTE_MCP_PUBLIC_URL=https://mcp.example.com
```

- ユーザーがログインに使うPoznoteの公開URLは、「設定 > 管理ツール > 管理者用Webhook」の「インスタンスのURL」です。リマインダーのメールやWebhookが使うのと同じURLです（これが空の場合は、`.env`の`POZNOTE_APP_URL`が使われます）。どちらも設定されていない場合は、管理者のブラウザーから自動で設定されます。インターネットからPoznoteにアクセスするときのアドレスになっているか確認してください。変更は、再起動しなくても1分以内にMCPサーバーに反映されます。「接続中のアプリ」のウィンドウには、使われているアドレスが管理者向けに表示され、ローカルのアドレスや暗号化されていないhttpのアドレスの場合は警告も表示されます。

うまくいかない場合：

- **アプリが、サーバーの認可（OAuth）の設定が見つからないと表示する**：ネットワークの外にあるマシンから、`https://mcp.example.com/.well-known/oauth-protected-resource/mcp`と`https://mcp.example.com/.well-known/oauth-authorization-server`を開いてください。どちらもJSONを返す必要があります。2つ目が`503`を返す場合は、Poznoteの公開URLが設定されていません。まったく応答がない場合は、リバースプロキシがMCPサーバーに届いていません。
- **アプリが開いたログインページが読み込まれない**：インスタンスのURLが、アプリからアクセスできるアドレスになっていません。「接続中のアプリ」の警告を確認し、「管理者用Webhook > インスタンスのURL」で修正してください。
- **起動時のMCPのログに`OAuth sign-in through Poznote enabled`が表示されない**：変数がコンテナーに届いていません。`.env`と`docker-compose.yml`を確認してから、コンテナーを作り直してください（`restart`では足りません）。
- **ログインはできるが、その後のリクエストがすべて失敗する**：コネクターのURLは、`POZNOTE_MCP_PUBLIC_URL`の後ろに`/mcp`を付けたものと完全に一致していなければなりません。一致していない場合は、MCPのログに`Rejecting a token issued for ...`と表示されます。
- `docker compose logs mcp-server`で、サーバーが何をなぜ拒否したかがわかります。`POZNOTE_DEBUG=true`にすると、すべてのリクエストも記録されます。

すべての接続に共通するルール：

- 接続は、使われている限り続きます。アプリは1時間ごとにアクセス権を更新し、90日間使われなかった場合は、もう一度ログインする必要があります。接続を解除したアプリも、最大で`POZNOTE_MCP_AUTH_CACHE_TTL`秒（既定は60秒）は動作し続けることがあります。
- `POZNOTE_MCP_SCOPE`は、引き続きすべての接続の上限になります。`write`に設定したサーバーに「フルアクセス」で接続しても、`write`になります。
- インスタンス全体に作用するツール（バックアップ、全体の設定、システム情報）には管理者のアカウントが必要です。また、リクエストで`user_id`を使って別のアカウントを指定することはできません。
- 接続したアプリは、アカウントのデータの送り先を変更できません。対象は、Git同期のリポジトリ、サーバー、トークンと、AIアシスタントと音声入力のエンドポイントとキーです。設定済みのリポジトリへのプッシュとプルは引き続き行えます。
- このモードが有効な間、`POZNOTE_MCP_AUTH_TOKEN`は無視されます。

#### 呼び出し元ごとの認証（任意）

上で説明した`POZNOTE_MCP_AUTH_TOKEN`は、1つの共有シークレットです。すべてのクライアントが同じトークンを提示し、サーバーは1つのプロフィールとして動作します。複数の人やエージェントで1つのMCPインスタンスを共有すると、それぞれを区別できません。

`POZNOTE_MCP_AUTH_PROVIDER`を設定すると、呼び出し元ごとの認証に切り替わります。各クライアントは**それぞれ専用の**トークンを提示し、そのトークンは外部のIDプロバイダーで照合されて、その呼び出し元のPoznoteのプロフィールに対応付けられます。1つのインスタンスで多くの呼び出し元を受け付け、それぞれを正しく識別できます。

これらの変数も、ほかの変数と同じく`.env`に書きます。変数は`mcp-server`サービスの`environment:`ブロックを通してMCPコンテナーに渡されますが、古い`docker-compose.yml`にはこれらが書かれていないため、その場合は何の表示もなく無視されます。設定する場合は、先に最新の`docker-compose.yml`をダウンロードし（[アプリケーションの更新](README.ja.md#アプリケーションのアップデート)を参照）、起動時にMCPのログに`Per-caller authentication enabled`と表示されることを確認してください。

| 変数 | 既定値 | 意味 |
|---|---|---|
| `POZNOTE_MCP_AUTH_PROVIDER` | *（未設定、機能はオフ）* | `userinfo`または`introspection`（`poznote`は[上記](#チャットアプリからのログインchatgptclaudegemini)で説明） |
| `POZNOTE_MCP_AUTH_URL` | *（必須）* | プロバイダーのエンドポイント |
| `POZNOTE_MCP_IDENTITY_MATCH` | `oidc_subject:sub` | `<profile-field>:<claim>`の組を、優先する順に並べたもの |
| `POZNOTE_MCP_AUTH_AUDIENCE` | *（未設定、機能はオフ）* | 想定する`aud`（カンマ区切り）。別のアプリケーション向けに発行されたトークンを拒否する |
| `POZNOTE_MCP_AUTH_HEADER` | `Authorization` | このサーバーが**プロバイダーに**送るヘッダー |
| `POZNOTE_MCP_AUTH_CLIENT_ID` / `_CLIENT_SECRET` | *（未設定、機能はオフ）* | `introspection`のみ。HTTP Basicとして送られる |
| `POZNOTE_MCP_AUTH_TIMEOUT` | `5` | 秒 |
| `POZNOTE_MCP_AUTH_CACHE_TTL` | `60` | 解決したトークンとプロフィールをキャッシュする秒数 |

`userinfo`は、呼び出し元のBearerトークンを付けて`GET <url>`を実行します。これはOpenID ConnectのUserInfoエンドポイントです。トークンはローカルでは検証されないので、不透明なトークンもJWTとまったく同じように使え、JWKSや鍵のローテーションのような管理の手間もありません。`introspection`は、`token=<token>`を付けて`POST <url>`を実行します（RFC 7662）。`active: false`を含む応答は、無効なトークンを意味します。

`POZNOTE_MCP_IDENTITY_MATCH`のクレームのうち、トークンに含まれていて、**かつ1つのプロフィールだけに一致する**最初のクレームが採用されます。プロフィールのフィールドは、`GET /api/v1/admin/users`が返すものです。既定ではサブジェクトだけで照合します。`preferred_username`や`email`での照合も使えますが、安全性は下がります。Poznote自身のログインでは、メールアドレスは確認済みの場合にしか照合しません。また、ユーザーがこれらのフィールドを編集できるプロバイダーでは、あるユーザーが別のユーザーのプロフィールを名乗れてしまいます。有効にするときは、意図したうえで選んでください。

2つのプロフィールに一致する値は、あいまいなものとして拒否されます。どのプロフィールにも一致しないIDも、そのまま拒否されます。既定のプロフィールに切り替えることは決してありません。既定のプロフィールはプロフィール1、つまり最初の管理者だからです。無効にしたプロフィールが照合の候補になることはありません。

有効にする前に知っておきたい2つの影響：

- **明示した`user_id`引数は、解決されたプロフィールと一致する場合にしか使えません**。ほとんどのツールがこの引数を受け付けますが、別のプロフィールを指定した引数は、受け入れられずに拒否されます。
- **`user_id`を受け付けないツール**（`get_system_info`、`list_backups`、`create_backup`、`delete_backup`）は、サーバーの既定のプロフィールとして動作します。そのため、これらを使えるのは、解決されたプロフィールが管理者である呼び出し元に限られます。

`POZNOTE_MCP_AUTH_PROVIDER`を設定すると、こちらが`POZNOTE_MCP_AUTH_TOKEN`より優先されます。そのトークンも設定したままの場合、サーバーはログに警告を出します。

#### ツールのスコープ

既定では、サーバーはすべてのツールを公開します。`POZNOTE_MCP_SCOPE`を使うと、3つのレベルのいずれかに制限できます。ノートの内容によって、呼び出すべきでないツールへと誘導されるおそれがあるので、無人で動くエージェントに役立ちます：

| レベル | ツール |
|---|---|
| `read` | 何も変更しないツールのみ：取得、一覧表示、検索、バックリンク、リビジョン、共有状態、システム情報、設定 |
| `write` | `read`に加えて、元に戻せる変更：ノート、タスク、リマインダー、フォルダー、移動、添付ファイル、ノートのゴミ箱への移動、ゴミ箱やリビジョンからの復元 |
| `admin` *（既定）* | 元に戻せない操作（ゴミ箱を空にする、ゴミ箱からの削除）、ワークスペース、バックアップ、Git同期、アプリの設定、公開リンクでの共有を含む、すべてのツール |

```bash
# .envに書き込む
POZNOTE_MCP_SCOPE=read

# 新しい環境変数を読み込ませるため、MCPコンテナーを作り直す
docker compose up -d --force-recreate mcp-server
```

レベルを超えるツールは、そもそも登録されません。クライアントには見えず、呼び出しても、クライアント側の表示や説明にかかわらず、不明なツールとして拒否されます。起動時のログに、レベルと公開されているツールの数が表示されます。不明な値を指定すると、`admin`にするのではなく、サーバーが停止します。

共有トークンを使う場合、レベルはサーバー全体に適用されます。2つのクライアントに別々のレベルを与えるには、専用の`POZNOTE_MCP_SCOPE`、ポート、`POZNOTE_MCP_AUTH_TOKEN`を持つ、2つ目のMCPコンテナーを動かしてください。

[呼び出し元ごとの認証](#呼び出し元ごとの認証任意)では、トークンのクレームに応じて、呼び出し元ごとにレベルを与えられます。`POZNOTE_MCP_SCOPE_MAP`には`<claim value>=<level>`の組を並べます。この値は、`POZNOTE_MCP_SCOPE_CLAIM`で指定したクレームと照合されます（既定は`scope`で、スペース区切りのOAuthスコープです。`groups`や`roles`のようなリスト形式のクレームも使えます）：

```bash
# IDプロバイダーが各クライアントに付与するOAuthスコープ
POZNOTE_MCP_SCOPE_MAP=poznote.read=read,poznote.write=write,poznote.admin=admin

# または、トークンにグループを含めるプロバイダーでは、グループ
POZNOTE_MCP_SCOPE_CLAIM=groups
POZNOTE_MCP_SCOPE_MAP=/poznote-agents=read,/poznote-users=write,/poznote-admins=admin
```

呼び出し元には、そのクレームが対応する最も高いレベルが与えられますが、`POZNOTE_MCP_SCOPE`を超えることはありません。それを超えるツールは、その呼び出し元のツールの一覧には表示されず、呼び出しても拒否されます。クレームがどのレベルにも対応しない呼び出し元は、サーバーのレベルを与えられるのではなく、そのまま拒否され（`401`）、その理由がログに記録されます。`POZNOTE_MCP_SCOPE_MAP`がない場合は、すべての呼び出し元にサーバーのレベルが与えられます。

すべてのツールには、MCP標準の`readOnlyHint`と`destructiveHint`のアノテーションも付いています。ツールを自分の側で絞り込んだり、呼び出しの前に確認を求めたりするクライアントは、これを利用できます。

#### デバッグモード

起動コマンドで`POZNOTE_DEBUG=true`を設定すると、ログのレベルが`INFO`から`DEBUG`に切り替わります。普段使うときは`false`に戻してください。認識されるのは、小文字の`true`と`false`だけです。それ以外の値は`false`として扱われ、MCPのログに警告が書き込まれます。Webサーバーのほうは許容範囲が広く、`1`、`on`、`yes`も受け付けます。Poznote APIに送るすべてのHTTPリクエスト、AIアシスタントから受け取るすべてのツールの呼び出し、すべての応答が、コンテナーのログに詳しく書き込まれます。接続や認証の問題を調べるときに使ってください：

```bash
docker compose logs -f mcp-server
```

普段使うときは無効にしておいてください。日常的には、これほど詳しいログは必要ありません。

## セキュリティ

MCPエンドポイントに到達できるクライアントに何ができるかは、[モード](#用途に合ったモード)によって異なります。

**クラシックモード**（既定）。エンドポイントに到達できる人は誰でも、すべてのプロフィールのすべてのノートを読み取り、作成、変更、削除でき（ツールは`user_id`引数を受け付けます）、バックアップ、復元、設定の変更も実行できます。次の2つの層によって、これが問題にならないようにしています：

1. **ネットワーク上の到達範囲**。既定では、エンドポイントにはローカルマシンからしかアクセスできません。
2. **受信用のBearerトークン**（任意）。`POZNOTE_MCP_AUTH_TOKEN`を設定すると、すべてのリクエストに`Authorization: Bearer <token>`が必要になります。

既定の`docker-compose.yml`なら、1つ目の層だけで十分です。完全には管理できない場所からポートにアクセスできるようになるときは、必ず2つ目の層を追加してください。

**チャットアプリからのログインと、呼び出し元ごとの認証**。すべてのリクエストに、1人のアカウントに結び付いたトークンが必要なので、クライアントはそのアカウントにだけ、与えられたレベルでアクセスします。この場合、エンドポイントはHTTPSの後ろに置き、インターネットからアクセスできるようにするのが前提です。チャットアプリは各社のサーバーから接続するためです。

どのモードでも、[ツールのスコープ](#ツールのスコープ)でクライアントにできることを絞り込めます。

### 127.0.0.1だけで待ち受けるのが普通で、しかも安全な理由

MCPコンテナーは、コンテナーの*内部*では`0.0.0.0`で待ち受けます（ポートマッピングを機能させるために、Dockerがこれを必要とします）。しかし、ポートは**ホストの`127.0.0.1`だけに**公開され、公開用のインターフェースに公開されることはありません：

```yaml
ports:
  - "127.0.0.1:${POZNOTE_MCP_PORT:-8045}:8045"
```

これは意図した設定で、正しい構成です。同じマシンで動いているプロセス（または、明示的に設定したSSHトンネル）だけが接続できます。既定の構成のままなら、心配することは何もありません。

### Dockerを使わずにMCPサーバーを動かす場合

`pip`でMCPサーバーをインストールし、`poznote-mcp serve`を自分で実行する場合（systemd、Proxmox LXCなど）は、前段にDockerのポートマッピングがないので、待ち受けるアドレスが重要になります：

- `poznote-mcp serve`は、**既定では`127.0.0.1`で待ち受けます**。ほかの設定が必要な理由がわかっている場合を除き、この既定のままにしてください。
- どうしても`0.0.0.0`で待ち受ける必要がある場合（別のホストにあるリバースプロキシ、VPNのインターフェース）は、`POZNOTE_MCP_AUTH_TOKEN`も設定してください。トークンなしでループバック以外のアドレスで待ち受けると、サーバーは起動時にログに警告を出します。
- 以前のリリースは、既定で`0.0.0.0`で待ち受けていました。`--host=127.0.0.1`を明示して渡してください（`serve`サブコマンドを使わずに実行する場合は、`MCP_HOST=127.0.0.1`を設定してください）。

### リモートアクセス

クラシックモードで、Poznoteがリモートのサーバーで動いていて、手元の作業用マシンから接続したい場合は、SSHのポートフォワーディングを使い、ポートを公開**しないで**ください（[チャットアプリからのログイン](#チャットアプリからのログインchatgptclaudegemini)では、HTTPSの後ろで公開することこそが目的なので、このセクションは当てはまりません）：

```bash
ssh -L 8045:127.0.0.1:8045 user@your-server
```

あとは、いつもどおりAIアシスタントの接続先を`http://127.0.0.1:8045/mcp`にします。

### 本番環境

MCPサーバーをネットワーク経由で使わなければならない場合は、次の方法で保護してください：
- `POZNOTE_MCP_AUTH_TOKEN`（[受信用の認証トークン](#受信用の認証トークン)を参照）、または[Poznoteを通したログイン](#チャットアプリからのログインchatgptclaudegemini)（各クライアントが、1つのアカウントに結び付いた、取り消し可能な専用のトークンを持ちます）。どちらの場合も、トークンが平文で送られないよう、前段にHTTPSを置く
- VPN（Tailscale、WireGuard）
- 必要に応じて、追加の層として、独自の認証やIPの許可リストを備えたリバースプロキシ（nginx、Caddy）。ただし、チャットアプリからのログインでは使えません。アプリは各社の、サーバーから接続し、そのIPアドレスは変わることがあります。また、リバースプロキシが別途求めるログインには応答できないため、エンドポイントとその`/.well-known/`のドキュメントには、常にアクセスできるようにしておく必要があります

### MCPサーバーがPoznoteに認証する方法

MCPサーバーは、`data/.mcp_token`に保存された内部用のBearerトークンを使って、Poznote REST APIに接続します。このトークンはPoznoteが自動で作成します。また、Docker Composeの構成では`./data`をMCPコンテナーに読み取り専用でマウントするので、トークンを`.env`に置く必要はありません。

このトークンはMCPサーバーを識別するので、このトークンを付けたリクエストがノートの内容やタスクを変更する直前に、Poznoteはそのノートのスナップショットを取ります（`update_note`、`add_task`、`update_task`、`complete_task`、`delete_task`、`add_subtask`、`update_subtask`、`delete_subtask`）。このスナップショットは、ノートの「リビジョン」ページに「MCPによる編集の前」として表示されるので、AIによる書き換えで内容が失われても、1回のクリックで復元できます。最新のスナップショットがすでに同じ内容を持っている場合は、スナップショットは取られません。安全用スナップショット（「AIによる編集の前」と「MCPによる編集の前」）は、ノートごとに直近の20件が保持されます。MCPサーバーの編集が多く、半日で20件を使い切ってしまうような場合は、「設定 > リビジョン」でこの数を増やしてください（最大200件）。

## 使用例

設定が済んだら、自然言語でPoznoteを操作できます：

```
ワークスペース「Poznote」のノートをすべて一覧表示して
「MCP」に関するノートを検索して
話し合いの内容について「議事録」というタイトルのノートを作成して
ノート123を新しい内容で更新して
ノート456をフォルダー「プロジェクト」に移動して
```
