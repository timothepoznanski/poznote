# Poznote AIアシスタント

ノートを検索して読むことができる、組み込みのAIチャットです。ローカルの[Ollama](https://ollama.com)や[LM Studio](https://lmstudio.ai)のインスタンス、[Anthropic（Claude）](https://www.anthropic.com)やOpenAIなどのクラウドプロバイダー、OpenAI互換の任意のサーバーで動作します。

> [!TIP]
> *外部*のAIアシスタント（VS Code Copilot、Claude CLIなど）をノートに接続したい場合は、[MCPサーバーのドキュメント](MCP-SERVER.ja.md)を参照してください。

## できること

設定が済むと、ノートのページとダッシュボードの左端にあるアイコンサイドバーに「AIアシスタント」ボタンが表示され、その場でチャットパネルを開けます。パネルは右側に固定されます。パネルを開いているかどうかと幅はページを移っても保たれ、会話も2つのページのあいだで引き継がれます。

アシスタントは**ノートを検索して読む**ためのツールを持っており、必要に応じて自分で使います。「Xについてノートには何と書いてある？」と尋ねたり、複数のノートにまたがる要約を頼んだり、うろ覚えのノートを探してもらったりできます。回答はストリーミングで表示され、Markdownとして整形されます。

はっきり頼んだ場合は、ノートに対して次の操作もできます。

- **書き込み**：ノートの作成、名前の変更、内容の書き換え。
- **整理**：タグの付け外し、フォルダーの一覧表示・作成・名前の変更、フォルダー間でのノートの移動、ノートやフォルダーのお気に入りへの追加。
- **日時**：ノートのリマインダー（1回限りまたは繰り返し）の設定と解除。アシスタントは設定したタイムゾーンでの現在の日時を知っているので、「来週の月曜9時にリマインドして」のような頼み方ができます。
- **タスク**：タスクリストのノートにあるタスクとサブタスクの追加、完了、完了の取り消し、名前の変更、削除（タスクの期限とリマインダーを含む）。通常のノートの中にあるチェックボックスのオンとオフも、ほかの部分を書き換えずに切り替えられます。
- **削除**：ノートや、フォルダー（サブフォルダーとその中のすべてのノートを含む）をゴミ箱に移動。どれも「ゴミ箱」ページから復元できます。アシスタントには、何かを完全に削除する手段も、ゴミ箱を空にするツールもありません。

開いているノートはコンテキストに含まれます。「このノートの書式を整えて」「ここに結論を足して」と言えば、IDやタイトルを指定しなくても、アシスタントはそのノートを対象にします。読むのはエディターが最後に保存した内容で、会話の途中で別のノートを開くと「このノート」もそちらに切り替わります。質問の中で別のノートを名指しした場合は、そちらが優先されます。ダッシュボードではノートを開いていないので、対象のノートを名前で指定してください。

入力欄の上の2行には、アシスタントが何を対象にしているかが表示されます。すべてのツールが動作する「ワークスペース」と、ノートを開いているときに「このノート」が指す「ノート」です。

アシスタントがノートを編集または作成すると、回答が終わった時点で、開いているノートとサイドバーが自動で更新されます。ページを再読み込みする必要はありません。アシスタントが編集したノートに保存していない変更がある場合は、代わりにバナーが表示されます。ノートを再読み込みするか、自分の編集内容を残して保存するかを選んでください。

アシスタントはノートの内容をMarkdownとして読み書きします。リッチテキスト（HTML）のノートは、「ノートを変換」と同じ変換処理でその都度双方向に変換されるため、書き換えても見出し、リスト、リンク、表、画像は保たれます。色やフォントなどの装飾は保たれません。アシスタントが全体を読み切れないほど長いノートは、途中で切り詰めて書き換えるのではなく、書き換え自体を断ります。

アシスタントがノートの内容を変更する前（書き換え、チェックボックス、タスク）に、Poznoteは現在の内容をリビジョンとして保存します。このリビジョンは、ノートの「リビジョン」ページ（ノートのツールバーにある履歴アイコン）に「AIによる編集の前」と表示されます。結果が期待どおりでなければ、そのリビジョンを復元してください。先に「変更点」タブを開いて、アシスタントが何を変えたかを確かめることもできます。最新のリビジョンがすでに同じ内容なら保存は省かれ、1回の回答で同じノートを何度変更しても、保存されるのは1件だけです。安全用リビジョン（「AIによる編集の前」と「MCPによる編集の前」）はノートごとに最新の20件が保持されます。この件数は「設定 > リビジョン」で変更できます（1〜200件）。

アシスタントの対象は**現在のワークスペースに限られます**。チャットを開いたワークスペースのノートだけを参照、検索、編集し、新しいノートもそこに作成します。別のワークスペースについて尋ねるときは、先にそのワークスペースに切り替えてください。複数のワークスペースを表示しているダッシュボードでは、アシスタントはそのすべてのワークスペースのノートをまとめて検索して読みます。ワークスペースをまたいで質問するには、この方法を使います。ただし、ここでは閲覧のみで、作成、編集、整理、削除は一切しません。見つけたノートを変更するには、そのノートかそのワークスペースを開いて、そこで頼んでください。

会話はPoznoteサーバー上の、ノートと同じ自分のデータベースに保存され、自分だけのものです。共有したワークスペースで作業している人には、その人自身の会話があります。パネルのヘッダーでは、プラスボタンで新しい会話を始められます。履歴ボタンではそのワークスペースの直近10件の会話を一覧表示し、続きを話したり削除したりできます。ゴミ箱ボタンは、画面に表示している会話を削除します。履歴は別のブラウザーや端末からも見られ、再読み込みすると、そのタブで開いていた会話が戻ります。

## アシスタントを有効にする

「設定 > 管理ツール > AIアシスタント」（管理者のみ）を開き、プロバイダーを選びます。

| プロバイダー | URL | APIキー |
|---|---|---|
| **Ollama**（ローカル） | Ollamaをどこで動かすか（コンテナーかホストか）によります。[ローカルのサーバーとDockerのネットワーク](#ローカルのサーバーとdockerのネットワーク)を参照 | 不要 |
| **LM Studio**（ローカル） | Dockerホストのアドレスとポート`1234`があらかじめ入力されます。[方法2](#方法2ホストにインストールしたollama)を参照 | 不要 |
| **Anthropic**（クラウド） | 自動で設定 | 必要 |
| **OpenAI**（クラウド） | 自動で設定 | 必要 |
| **その他（カスタムURL）** | OpenAI互換の任意のベースURL | サーバーによる |

次に「アクセスを確認してモデルを一覧表示」を押します。サーバーに接続できるかを確かめ、サーバーが提供するモデルを「モデル」のドロップダウンに読み込みます。この確認が成功するまでドロップダウンは空のままなので、モデルを選ぶにはこの手順が必要です。

この設定はインスタンス全体に適用されます。管理者が有効にすると、すべてのユーザープロフィールでチャットが使えるようになります。

### 個人のAPIキー

同じページに「個人のAPIキーを許可」というオプションがあります。有効にすると、各ユーザーの設定に「自分のAIアシスタント」カードが表示され、インスタンスで設定されたものの代わりに、自分のサーバー、プロバイダー、APIキーでチャットを使えるようになります。

## モデルの選び方

`qwen3`、`llama3.1`、`mistral`など、**ツール呼び出し**（「function calling」とも呼ばれます）に対応したモデルを選んでください。アシスタントがノートを参照できるのは、ツール呼び出しがあるからです。対応していないモデルでもチャットは使えます（その旨の通知が表示されます）が、アシスタントが自分でノートにアクセスすることはできません。

### 推論の深さ

推論モデル（OpenAIのGPT-5やoシリーズ、Ollamaの`gpt-oss`など）は、回答する前にどれだけ考えるかを決める**推論の深さ**（reasoning effort）を受け付けます。これは設定ページの「推論の深さ」欄で指定します。「自動」（既定）では何も送らずにプロバイダーに任せます。「なし」「最小」「低」「中」「高」「最高」を選ぶと、すべてのリクエストに`reasoning_effort`パラメーターとして送られます。モデルが受け付けない値はプロバイダーに拒否され、チャットにエラーとして表示されます。

OpenAIの一部のモデルは、推論の深さが`none`でないと、Chat Completions APIでのツール呼び出しを拒否します。その場合、チャットには、アシスタントがノートを参照できないという通知が表示されます。「推論の深さ」を「なし」にすると、ツールが使えるようになります。

### カスタムヘッダー

モデルの手前に置くゲートウェイ（LiteLLM、OpenRouter、Cloudflare AI Gateway、Heliconeなど）は、呼び出し元の識別や使用量の割り当てのために、独自のヘッダーを求めることがよくあります。こうしたヘッダーは、設定ページの「カスタムヘッダー」欄に、1行に1つずつ`Name: value`の形で入力します。

```
x-litellm-customer-id: poznote
```

ヘッダーは、接続の確認も含めて、AIサーバーへのすべてのリクエストで送られます。この欄はどのプロバイダーでも、インスタンスの設定と個人の設定の両方にあります。Anthropicでは、ワークスペースに限定されていない組織のAPIキーに`anthropic-workspace-id: wrkspc_...`が必要です。OpenAIでは、`OpenAI-Organization`と`OpenAI-Project`で、課金先の組織やプロジェクトを選びます。

値は暗号化して保存され、二度と表示されません。保存したヘッダーは`Name: ••••••••`と表示されます。値を変えないときはその行をそのままにし、変えるときは値を入力し直し、ヘッダーを削除するときはその行を消します。

リクエストの形を決めるヘッダー（`Host`、`Content-Type`、`Content-Length`、`Accept`など）は受け付けません。「APIキー」欄で設定される`Authorization`も受け付けません。Anthropicでは、Poznoteが設定する`x-api-key`と`anthropic-version`も受け付けません。名前と値に使えるのはASCII文字だけで、ヘッダーは20個までです。

また、ゲートウェイのログで送信元がわかるように、すべてのリクエストに`User-Agent: Poznote/<version>`が付きます。カスタムヘッダーに`User-Agent`の行を書くと、それに置き換わります。

## カスタム指示

各ユーザーは「設定 > 自分のAIアシスタント > カスタム指示」で、アシスタントにいつも守ってほしい指示を与えられます。たとえば「英語でノートを書いたときは、その下に日本語訳を追加してください。逆の場合も同様です」といった指示です。このテキスト（最大4000文字）は、アシスタントがインスタンス用と個人用のどちらの設定で応答する場合も、すべてのメッセージと一緒にモデルに送られます。口調、言語、アシスタントが書くノートの形式など、継続的な好みの指定に使ってください。アシスタントに許される操作は変わりません。ノートが変更されるのは、これまでどおり頼んだときだけです。空欄にすると何も送りません。

## 保存したプロンプト

「このノートの文法と構成をチェックして、改善点を提案してください」や「ほかに聞いておくべき質問はありますか？」のように、よく送るプロンプトは「設定 > 自分のAIアシスタント > 保存したプロンプト」に保存できます。それぞれに名前と本文を付け、30件まで保存できます。チャットでは、入力欄の横にある稲妻のボタンで一覧を開き、1つをクリックすると、その本文が自分のメッセージとして送られます。本文に「このノート」とあれば、開いているノートが対象になります。入力途中の文は入力欄にそのまま残ります。カスタム指示と違い、保存したプロンプトは選んだときだけ送られます。一覧の下にある「保存したプロンプトを管理」を押すと、設定が開きます。プロンプトを削除するには、そのゴミ箱アイコンをクリックするか本文を空にしてから、保存します。

## 外部ツール（MCPサーバー）

アシスタントは、自分のツールに加えて、リモートの[MCP](https://modelcontextprotocol.io)サーバーが提供するツール（たとえばWeb検索サービス）を呼び出せます。これにより、回答したりノートを書いたりする前に、最新の情報を調べられます。これは、ほかのアシスタントからノートにアクセスできるようにする[PoznoteのMCPサーバー](MCP-SERVER.ja.md)とは逆向きの仕組みです。

この機能は既定ではオフです。管理者が「設定 > 管理ツール > AIアシスタント」の「外部ツール」セクションで「外部ツールを許可」をオンにし、そこにサーバーを追加します。入力するのは、名前、MCPエンドポイントのURL（例：`https://mcp.exa.ai/mcp`）、Bearerトークンとして送られるAPIキー（任意）、別の方法でキーを受け取るサーバー向けのカスタムヘッダー（任意）です。Poznoteはサーバーに接続して、提供されているツールを読み込み、それぞれにチェックボックスを付けて一覧表示します。アシスタントに呼び出しを許すツールを、ここで選びます。これらのサーバーは、インスタンスのアシスタントを使えるユーザーに提供されます。「ユーザーが自分のサーバーを接続することを許可」をオンにすると、各ユーザーの「設定 > 自分のAIアシスタント」にも「外部ツール」セクションが表示され、自分の会話だけで使うサーバーを追加できます。

対応しているのは、APIキーかカスタムヘッダーを使ってHTTP（Streamable HTTPトランスポート）で接続するサーバーだけです。ローカルのプロセスとして起動するサーバー（stdio、`npx ...`）や、OAuthが必要なサーバーには対応していません。AIサーバーと同じく、MCPサーバーはPoznoteサーバーから呼び出されるため、そのURLにはコンテナーの中から接続できる必要があります。ツールが読み込まれるのは、サーバーを追加したときと、「確認してツールを更新」をクリックしたときです。サーバーがあとからツールを追加したり説明を変えたりしても、更新するまでは使われません。

サーバーを接続すると、チャットの入力欄の横に地球儀のボタンが表示されます。このボタンで外部ツールのオンとオフを切り替えられ、選んだ状態はブラウザーに記憶されます。ツールの呼び出しはすべて、サーバー、ツール、送った内容とともに会話の中に表示されます。

外部ツールが返す内容は、WebページなどPoznoteの外から来たもので、モデルを欺くために書かれたテキストが含まれていることがあります。アシスタントにはそれをデータとして扱うよう指示してあり、ノートを変更する前にはリビジョンも保存されますが、指示は保証にはなりません。意図しない変更を確実に防ぐには、「設定 > 自分のAIアシスタント」の「アシスタントのツール」セクションを開き、「ノートの変更」の一覧にあるツールのチェックを外してください。アシスタントはノートの読み取りやWeb検索はできますが、何も変更できなくなります。また、アシスタントが外部ツールに送った内容はインスタンスの外に出ることにも注意してください。

## ローカルのサーバーとDockerのネットワーク

AIサーバーは、ブラウザーからではなく、必ず**Poznoteサーバーから**呼び出されます。PoznoteはDockerコンテナーの中で動くため、設定するURLには*そのコンテナーの中から*接続できる必要があります。

ローカルのOllamaには**2通りの構成**があり、どちらも完全にサポートされています。

| 構成 | 設定するURL | ネットワークの設定 |
|---|---|---|
| [**方法1**：DockerコンテナーとしてOllamaを動かす](#方法1dockerコンテナーとしてollamaを動かす最も簡単) | `http://ollama:11434` | 不要 |
| [**方法2**：ホストにインストールしたOllama](#方法2ホストにインストールしたollama) | コンテナーから見たホストのアドレス | 必要。多くの人がつまずくのはここです |

一から始めるなら方法1を選んでください。Ollamaがすでにマシンにインストールされている場合や、ほかのアプリケーションでも使っている場合は、方法2を選んでください。

### 方法1：DockerコンテナーとしてOllamaを動かす（最も簡単）

群を抜いて簡単なのは、ホスト側でOllamaを動かさない構成です。Poznoteと同じ`docker-compose.yml`に、Ollamaを別のサービスとして追加します。

```yaml
  ollama:
    image: ollama/ollama
    container_name: ollama
    restart: always
    volumes:
      - "./ollama:/root/.ollama"
```

次に、起動してモデルを取得します。

```bash
docker compose up -d
docker exec ollama ollama pull qwen3
```

AIアシスタントの設定で、あらかじめ入力されているURLを`http://ollama:11434`に置き換えます。同じcomposeファイルのサービスはDockerネットワークを共有し、サービス名で互いに接続できるため、ほかに設定することはありません。公開するポートも、設定する`OLLAMA_HOST`もなく、OllamaがDockerネットワークの外に公開されることもありません。composeファイルで独自の`networks`を定義している場合は、`ollama`をPoznoteのサービスと同じネットワークに入れてください。

コンテナーの中でGPUによる高速化を使う方法は、[OllamaのDockerイメージのドキュメント](https://hub.docker.com/r/ollama/ollama)を参照してください。

### 方法2：ホストにインストールしたOllama

Ollamaをホストマシンで直接動かしている場合（[ollama.com](https://ollama.com)からの標準のインストール）や、LM Studioを使っている場合も、Poznoteから接続できます。ただし、コンテナーからDockerのネットワークを通ってホストにたどり着けるようにする必要があります。その方法を以下で説明します。

#### `localhost`ではうまくいかない理由

`http://localhost:11434`や`http://127.0.0.1:11434`では接続**できません**。コンテナーの中では、`localhost`はOllamaを動かしているマシンではなく、コンテナー自身を指すからです。Dockerはコンテナーごとに、隔離された専用のネットワークスタックを与えます。物理的には同じマシンでも、「localhost」は2つあるということです。

ホストに接続するには、コンテナーはDockerネットワークの**ゲートウェイ**を経由する必要があります。ゲートウェイは、ホストが持っているIPアドレスです。

#### 正しいURLを見つける

Poznoteは、Dockerホストのアドレスとして最も可能性が高いものを、次の順に探してURL欄にあらかじめ入力します。

1. コンテナーの中で名前解決できる場合は`host.docker.internal`（Windows/macOSのDocker Desktopでは常に解決できます。Linuxでは、下記の設定で割り当てた場合だけです）。
2. それ以外の場合は、コンテナーのルーティングテーブルから読み取ったデフォルトゲートウェイのIP（例：`http://172.17.0.1:11434`）。

あらかじめ入力されたURLで、たいていはそのまま動きます。自分で確かめる場合は、ホストで次を実行します。

```bash
docker exec <poznote-webserver-container> ip route | grep default
# default via 172.17.0.1 dev eth0   ← このゲートウェイのIPが、コンテナーから見たホストです
```

Linuxでも、`docker-compose.yml`の`webserver`サービスに次を追加すると、（Docker Desktopと同じように）`host.docker.internal`を使えるようになります。

```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
```

そのあと`docker compose up -d`を実行します。URLは`http://host.docker.internal:11434`になります。このURLは変わらず、どのマシンでも同じです。

#### コンテナーからの接続をOllamaで待ち受ける

既定では、Ollamaはホストのループバックである`127.0.0.1`でしか待ち受けません。ここには、ゲートウェイのIPが正しくても、どのコンテナーからも接続できません。`OLLAMA_HOST`を設定して、コンテナーから接続できるインターフェイスで待ち受けるようにする必要があります。

Linuxに標準の方法でインストールした場合（systemd）は、次を実行します。

```bash
sudo systemctl edit ollama
```

次を追加します。

```ini
[Service]
Environment="OLLAMA_HOST=172.17.0.1:11434"
```

そのあと、次を実行します。

```bash
sudo systemctl restart ollama
```

待ち受けるアドレスの選び方は次のとおりです。

- **`172.17.0.1`（`docker0`ブリッジ。Linuxでのおすすめ）**：すべてのコンテナーから接続でき、どのDocker環境にも存在し、外部には公開されません。`docker0`のIPは`ip addr show docker0`で確かめてください（Dockerのアドレスプールを変更していなければ`172.17.0.1`です）。
- **`0.0.0.0`**（すべてのインターフェイス）：最も簡単ですが、マシンの**すべての**インターフェイスでOllamaが公開されます。Ollamaには認証がないため、マシンにパブリックIPがある場合は、そのポートを遮断するファイアウォール（例：`ufw deny 11434`）の内側でだけ使ってください。NATの内側にある家庭のマシンなら問題ありません。
- 特定のComposeネットワークのゲートウェイ（例：`192.168.48.1`）：動作はしますが、このサブネットはネットワークの作成時にDockerが自動で割り当てるもので、ネットワークを作り直すと変わることがあるため、避けてください。

Docker Desktop（Windows/macOS）でOllamaをホストで動かしている場合は、`OLLAMA_HOST=0.0.0.0`にするのが一般的です。通常、そのマシンは外部に直接公開されておらず、`host.docker.internal`で追加の設定なしに接続できます。

**LM Studio**も同様です。サーバーの設定で「Serve on Local Network」（`0.0.0.0`で待ち受けるのと同じ）を有効にしてください。有効にしないと`127.0.0.1`でしか待ち受けません。

#### 接続を確かめる

ホストで、Ollamaが実際にどこで待ち受けているかを確かめます。

```bash
ss -tlnp | grep 11434
```

続いて、Poznoteが使うURLそのものを、コンテナーの中からテストします。

```bash
docker exec <poznote-webserver-container> curl -s -m 3 http://172.17.0.1:11434/
# "Ollama is running"
```

何も返ってこない場合、問題はPoznoteではなく、Ollamaの待ち受けアドレスかファイアウォールにあります。設定ページの「アクセスを確認してモデルを一覧表示」ボタンも同じ確認を行い、成功するとモデルのドロップダウンに一覧を読み込みます。

## 接続エラー

AIサーバーが何も応答しないうちに失敗したリクエスト（DNSのタイムアウト、接続の拒否、終わらないTLSハンドシェイクなど）は、短い間隔をおいて自動で送り直され、続けて最大3回まで試行されます。そのあいだ、チャットには「再試行しています」という行が表示されます。サーバーはまだ応答を始めていないので、失われるものはありません。最後の試行も失敗すると、チャットにエラーと「再試行」ボタンが表示されます。このボタンを押すと、入力し直さずに同じメッセージをもう一度送れます。

回答のストリーミングが始まったあとに起きたエラーは、回答の一部がすでに画面に出ているため、自動では再試行されません。「再試行」ボタンを使ってください。

## プライバシー

AIサーバーは、ブラウザーからではなく、必ずPoznoteサーバーから呼び出されます。ローカルのOllamaやLM Studioのインスタンスを使う場合、ノートや会話がマシンの外に出ることはありません。クラウドプロバイダーを使う場合は、アシスタントが回答のために読んだノートの部分が、そのプロバイダーに送られます。外部ツールをオンにしている場合は、アシスタントが外部ツールに送る内容（検索クエリなど）が、接続したサーバーに届きます。
